二、经验教训

教训 1：subagent 禁止后台下载。B/D 分支首轮失败的直接原因是把批量 PDF 下载挂到裸 shell 后台——subagent 会话结束时进程被清理，下载静默失败且无任何完成信号。规则：subagent 内一切下载必须前台同步执行、逐篇确认文件落盘；确需后台必须走 harness 后台机制（框架跟踪、完成通知、输出落 task 文件）。
教训 2：先落盘底稿，再下载归档。重派后的 B/D 采用"先写完底稿正文（调研结论不依赖 PDF 本体），再集中下载登记"的顺序，即使下载环节再出问题，调研成果也不会丢——把最贵的产出（综合与判断）放在最脆弱的环节（网络下载）之前。
教训 3：并行 agent 写索引用片段文件，合并交给单点。四分支各写 index_fragments/{A..D}.yaml，由 main-agent 用脚本统一合并去重——全程零写冲突。代价是需要一次显式合并（本次处理了 3 组重复、13 个孤儿、2 个别名副本），但比并发写共享文件的随机损坏便宜得多。孤儿与别名副本的产生也提示："下载即登记"的纪律在并行场景仍会漏，合并时必须做文件系统 ↔ 索引的双向核对。
教训 4：完成判定看真实产出。本次能及时发现 B/D 失败，靠的是 main-agent 不轻信 subagent 的"任务完成"信号，而用 ls/Read 核实 PDF 文件与索引条目——CLAUDE.md 第 3 节的这条规则在首个 change 就兑现了价值。
